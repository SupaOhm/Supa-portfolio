## Images (DevTools > Network, disable cache, hard reload)

- [x] Filter to Img. Total transferred for `/images/projects/*` is ~278 KB, not ~6.8 MB.
      — **280.1 KB** (286,808 bytes) over the wire for all 11 distinct images
      with the cache disabled, against **278.3 KB** (284,952 bytes) on disk. The
      ~1.8 KB delta is HTTP response-header overhead, ~160 bytes per request.
      Nowhere near 6.8 MB.
      Worth knowing: that 280 KB figure requires *grid* view, which mounts every
      card. A default visit lands in carousel view, which mounts only 5 slots and
      therefore transfers **107 KB across 5 images**. The real-world first-visit

      Note: `revrace` is not among the 5 carousel slots, so it only transfers at

## What no test in this branch proves

- ~~The 278 KB figure is measured with `stat` on encoded files, not observed
  over the wire.~~ **Superseded 2026-08-16:** now observed over the wire at
  280.1 KB with the cache disabled. The `stat` total (278.3 KB) and the wire
  total agree to within HTTP header overhead.
- `loading="lazy"` — jsdom implements no lazy loading. The test asserts only
  that the attribute is present. The browser checks in this document remain the
  sole evidence of real deferral; that is unchanged, the evidence is just now
  recorded from two independent passes.
- The 4 → 2 → 0 request progression — the cache tests use a fake `fetch` and
  injected fake storage. No test observes a real network request. Still true of
  the **suite**; the counts themselves are now observed over a real network
  stack here (2 cold, 0 within TTL, 2 after TTL expiry, 2 in a new tab).
- Real `sessionStorage` is never exercised by the suite; storage is injected
  precisely so tests avoid it. Real `sessionStorage` **is** exercised in this
  document, including its throwing-`setItem` failure mode. Safari itself
  remains manual-only.
- No test renders inside `<StrictMode>`. The hook's `let applies = true` flag
  exists specifically for React's dev-mode mount→cleanup→remount sequence,
  and review traced it as correct by construction — but no executable test
  exercises it. The "StrictMode / navigation" checks above are the only real
  evidence, and they now carry measured numbers: the double-mount produced 2
  requests, not 4, and the round trip produced 0.
- The mid-flight-unmount jsdom test is a smoke test, not a guard. It was
  verified adversarially to pass both against an unwired hook and against a
  variant with a real per-consumer `AbortController` restored. The reason is
  structural: cancelling the shared request could only be introduced inside
  `getCachedGitHubProfile`, which takes no `AbortSignal` at all. The design
  is protected by an absent parameter, not by an assertion. If someone adds
  a signal parameter to that function, no test will stop them — which makes
  the navigation check above the real safety net.
- The shared-promise rejection path is untested for two concurrent
  consumers. Both `About` and `Connect` should show their empty state when
  the single shared fetch fails; that is covered by the "GitHub failure
  modes" checks above, not by the suite.
