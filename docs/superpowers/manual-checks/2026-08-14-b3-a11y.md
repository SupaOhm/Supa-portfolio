# Slice B3 — Manual accessibility verification

Originally written against the Vercel preview for branch `fix/a11y-polish`, with
the note that nothing here was automatable: "jsdom computes no colour and has no
layout engine, and no browser automation is connected to this environment."

**Resolved 2026-08-16 against production (`https://supakornohm.vercel.app/`)**
using headless Chrome driven over the DevTools Protocol. That is a real layout
and paint engine, so the colour and geometry items became measurable. Method
notes are recorded per section; where the method is weaker than the original
intent, that is stated rather than glossed.

Tick each line only after observing it. An unticked line is an open risk, not
a formality.

## Contrast (measured, not eyedropped)

Method: foreground from `getComputedStyle().color`; background sampled as the
**modal pixel** of the element's box in a real screenshot, so gradients,
`backdrop-blur`, and alpha layers are resolved by the renderer rather than by
arithmetic. Self-check: the `SYS_ACTV` background sampled as exactly
`rgb(17,24,39)` = `#111827` = Tailwind `gray-900`, which is what the markup
declares — confirming the sampler reads true composited output.

- [x] Hero's "Hola World" eyebrow: contrast >= 4.5:1. — **7.93:1**
      (`#9CA3AF` on `#030712`, 12px).
- [x] Hero's `SYS_ACTV` badge on its `gray-900` ground: >= 4.5:1. — **6.99:1**
      (`#9CA3AF` on `#111827`, 10px).
- [x] A category count `(n)` inside the open filter dropdown: >= 4.5:1. —
      **6.98:1** (`#9CA3AF` on `rgb(17,24,40)`, 12px). Both the pixel-derived
      and computed-colour routes agree to 2dp here.
- [x] An inactive carousel dot against the page: >= 3:1. — **4.16:1**
      (dot painted exactly `rgb(107,114,128)` = `gray-500`, page `#030712`).
- [x] A side carousel card's description text against that card's own
      background: >= 4.5:1. — **4.98:1**, close to the 4.86:1 Slice C1 computed.

### How the side-card number was derived, and one method that was rejected

A side card is dimmed by a group `opacity: 0.8` on an ancestor, so its computed
`color` is *not* what gets painted and would overstate contrast. A
frequency-based "glyph core" pixel sampler was written for this, then **failed
its validation** and was discarded: run against the hero eyebrow, whose true
foreground is known to be `#9CA3AF`, it returned the background instead
(ratio 1.01) — that `<p>` is a full-width block with wide letter-spacing, so no
single antialiased RGB value clears a frequency threshold.

The number above instead uses the fact that group opacity scales text and card
background identically against the page backdrop:

    rendered_fg = op*declared_fg + (1-op)*backdrop     (derived)
    rendered_bg = op*card_bg     + (1-op)*backdrop     (sampled directly)

Validation: running the identical derivation on the **centre** card (`op == 1`)
returns exactly the declared `rgb(156,163,175)`, and that card measures 7.38:1.

## Screen reader semantics

**Method, and its limit.** These were verified against Chrome's computed
accessibility tree (`Accessibility.getFullAXTree`) — the same tree Chrome
exposes to VoiceOver through the platform accessibility API — plus the live
regions' actual text content and `document.activeElement` across each
interaction. This proves the roles, accessible names, states and structure that
VoiceOver reads out. It does **not** prove VoiceOver's speech synthesis, its
rotor UI, or its verbosity settings. If you want belt-and-braces on the spoken
strings themselves, a real VoiceOver pass is still the only way.

### Finding: the GitHub heading's accessible name runs together

`About.tsx:105-115` renders `<h3>GitHub Activity<a>@SupaOhm ↗</a></h3>`. The
separation is `ml-3`, a **margin**, which contributes no character to accessible
name computation, so the name concatenates to:

    "GitHub Activity@SupaOhm ↗"

It is announced with no pause between "Activity" and "@SupaOhm", and the `↗`
is announced as its Unicode name. This does not violate the checklist item
above — the item is about the GitHub *display name* (the API's `name` field),
which genuinely is absent from the heading tree — so that box stands ticked.
This is a separate, newly found defect. Not fixed here; no test covers it.
