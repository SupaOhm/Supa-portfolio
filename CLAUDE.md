# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start Vite dev server (host `0.0.0.0`, port `5173`, exposed on LAN)
- `npm run build` — type-check (`tsc -b`) then build to `dist/`
- `npm run lint` — run ESLint over the repo
- `npm run preview` — serve the production build locally
- `npm run images` — re-encode project image originals in `assets-src/projects/` into the 800px `.webp` files under `public/images/projects/` (`scripts/optimize-images.ts`). Manual/local only, never run in CI. Requires macOS (`sips`) and `cwebp` (`brew install webp`), plus Node 22.18+/23.6+ specifically for this command — it executes a bare `.ts` file, which needs Node's unflagged native type stripping and fails on the project's Node 20 `engines` floor with a parse error rather than a friendly message.
- `npm run og` — render `assets-src/og/og.html` to the 1200×630 `public/og.png` Open Graph card (`scripts/render-og.ts`) via headless Chrome, with the Chrome binary path hardcoded for macOS. Manual/local only, never run in CI — same trap as `npm run images`: it executes a bare `.ts` file, which needs Node 22.18+/23.6+ for unflagged native type stripping and fails on the project's Node 20 `engines` floor with a parse error rather than a friendly message.

`npm test` runs the Vitest suite (280 tests across 34 files); `npm run typecheck` runs a standalone `tsc -b --noEmit`.

The suite's default `environment` is `'node'`. Files that need a DOM opt in individually with `// @vitest-environment jsdom` as their **first line** — there is no global jsdom. `src/test/setup.ts` runs for every file regardless, and guards its whole body behind `typeof window !== 'undefined'` for exactly that reason.

**`src/test/setup.ts` stubs `matchMedia`, `IntersectionObserver` and `scrollIntoView` deliberately inert** — `matchMedia` always reports `matches: false` and its `addEventListener` never fires; the `IntersectionObserver` stub records nothing. That is correct for its job (stopping component tests throwing on mount) but it means a test written against the default environment for reduced-motion or reveal behaviour **passes while asserting nothing**. `src/test/doubles.ts` exists for that case: controllable versions of those globals plus `stubRect`, imported only by the files that drive them, so `setup.ts` never has to change under the tests that depend on it. jsdom also performs no layout, so every `getBoundingClientRect()` returns zeros while `innerHeight` is 768 — `stubRect` is what makes geometry-dependent tests real rather than vacuous.

## Architecture

Single-page React 19 portfolio built with Vite, TypeScript, and Tailwind CSS v4. No backend — all dynamic data comes from the public GitHub REST API at runtime.

**Routing vs. single-page sections is the key thing to understand.** `pages/Home.tsx` (mounted at `/`) stacks `Hero`, `About`, `Skills`, `Projects`, and `Connect` together, and that single scrolling page is the actual UX. `App.tsx` declares routes for `/about`, `/projects`, and `/connect`, but each renders `<RedirectToSection id="...">` (`src/pages/RedirectToSection.tsx`), which returns `null` and, in an effect, immediately `navigate('/', { replace: true, state: { targetId: id } })`s — these paths never render `About`, `Projects`, or `Connect` directly, only redirect to the section on `/`. A catch-all `*` route renders `NotFound` (`src/pages/NotFound.tsx`) for any other URL; because `vercel.json` rewrites every unmatched path to `index.html`, this is what actually displays instead of a blank page. Navigation on the canonical page works by scrolling to section IDs, not by switching routes:
- `Navbar` highlights the active section with `useActiveSection` (`src/hooks/useActiveSection.ts`), which is a window `scroll` listener, **not** an `IntersectionObserver`: it measures what fraction of the viewport each section occupies, picks the largest, and ignores anything under 10%. It also re-measures on `transitionend` on `#about`, so the About section's expand/collapse updates the highlight, and it is disabled entirely off `/`. The only `IntersectionObserver` in the app is in `useReveal.ts`. Clicking a link scrolls via `el.scrollIntoView({ behavior: currentScrollBehavior() })` written inline in `handleSectionClick` (`src/components/Navbar.tsx:32`) — a second copy of that call, separate from the `scrollToSection` export that `Home.tsx` uses.
- `Home.tsx` reads `location.state.targetId` (or the URL hash) on mount and calls `scrollIntoView` to jump to a section (`src/pages/Home.tsx:13-19`).
- Because the navbar is `fixed`, it is out of flow and a scrolled-to section knows nothing about it. `scroll-padding-top` on `html` in `src/index.css` is what stops each jump landing the section behind the bar, and it covers `scrollIntoView`, `#hash` links and browser scroll restoration in one place — do not reach for per-section `scroll-mt`. Its two values have to track `Navbar.tsx`'s `top-0`/`h-14` and `sm:top-6`/`sm:h-16` classes, and nothing in the browser links a stylesheet number to a class name, so `scripts/scroll-offset.test.ts` parses both files and fails if they disagree.

When editing navigation, treat `/about`, `/projects`, `/connect` as redirect-only entry points, not as pages that render their own content — the primary path renders everything inside `Home`.

**`vercel.json`** is the only production deploy config in the repo and is the entire fix for a real bug: before it existed, `/about`, `/projects`, and `/connect` 404'd in production because Vercel's static host has no knowledge of client-side routes. It must use the `rewrites` property — never the legacy `routes` property. Per Vercel's docs, `rewrites` "checks the filesystem by default" and "precedence is given to the filesystem prior to rewrites being applied," so `/images/...` and other static assets keep resolving normally; `routes` has no such default and requires an explicit `{"handle": "filesystem"}` phase before a catch-all entry, so a naive conversion from `rewrites` to `routes` without that phase would 404 every image and static asset on the site. **No test guards this file** — `vite preview` returns 200 and the SPA shell for all three routes even with `vercel.json` absent, so nothing local can distinguish a correct config from a missing one; changes here need manual verification against a real Vercel deploy.

**Project data lives in `src/data/projects.ts`** as the `PROJECTS: Project[]` array; `README.md:108` agrees, so both are current. The `Project` type and the allowed `ProjectCategory` / `ProjectStatus` string-literal unions are defined in `src/types/project.ts` — add new categories/statuses there first, since they are `as const` tuples that drive both typing and filter UI. Project images are static assets under `public/images/projects/` referenced by absolute path (e.g. `/images/projects/expense.webp`). Originals live in `assets-src/projects/`, outside `public/` so Vite never deploys them but they stay in-repo so the encoder script stays reproducible; `public/images/projects/` holds the generated 800px `.webp` files that `src/data/projects.ts` actually references.

**GitHub integration** is consumed by both `About.tsx` (compact snapshot) and `Connect.tsx` (detailed insights), but the fetch is **not** duplicated: both call `useGitHubProfile(GITHUB_USERNAME)` (`About.tsx:71`, `Connect.tsx:70`), which routes through `getCachedGitHubProfile` in `src/lib/githubCache.ts`. That module dedupes concurrent callers against a module-level in-flight map and caches the result in `sessionStorage` under a 10-minute TTL (`CACHE_TTL_MS`), so two mounted consumers produce **one** network request, not two. What is still duplicated is only the `GITHUB_USERNAME = 'SupaOhm'` / `GITHUB_PROFILE_URL` constant pair, declared separately in each component.

There is no auth token, so requests still count against GitHub's unauthenticated rate limit (60 req/hr/IP), but the dedupe and TTL make exhausting it during local reloading much less likely than the raw call count suggests. Both components already optional-chain every field, so a failed or malformed response renders blanks rather than crashing.

**Projects.tsx** holds the most complex UI: a 3D perspective carousel (center card scaled/full brightness, neighbors rotated and dimmed for depth) plus a grid view toggle and category filtering with count badges. Animations are CSS/Tailwind-driven; global keyframes live in `src/index.css`.

**`assets-src/` vs `public/`**: `assets-src/` holds source material that must stay in-repo for reproducible re-encoding but must never ship as-is. `assets-src/projects/` holds the original, unoptimized project images; it lives outside `public/`, so Vite never bundles or deploys it, but it stays in-repo (not gitignored) so `npm run images` (the `scripts/optimize-images.ts` encoder) can be re-run reproducibly against the same sources. `public/images/projects/` holds only the generated, 800px-wide `.webp` output that `src/data/projects.ts` actually references — that's what ships. The same pattern repeats for the Open Graph card: `assets-src/og/og.html` is the source template, and `npm run og` (`scripts/render-og.ts`) renders it via headless Chrome into `public/og.png`, the 1200×630 image the `og:image` meta tags in `index.html` reference — that's the generated artifact that ships. `public/` also holds two hand-authored discoverability artifacts that are not generated by any script: `robots.txt` (permissive crawl policy plus an absolute sitemap pointer) and `sitemap.xml` (one URL, `/` only — `/about`, `/projects` and `/connect` are excluded because each serves an `index.html` declaring `canonical:/`, making them non-canonical by the site's own statement). Both hardcode the deployed origin, as does the JSON-LD block in `index.html`, `README.md`, and (as a bare host with no scheme) `assets-src/og/og.html`; `scripts/site-origin.ts` holds the single `ORIGIN` definition and `scripts/discoverability.test.ts` guards all five of those source files, failing if any disagrees with it. None of them can import the constant, so the test is the enforcement, not the import. `public/og.png` is the one exception: it's a rendered binary carrying the origin as pixels, so no test can check it — a domain change needs a manual `npm run og` re-render on top of the guarded-file edits.

**`scripts/` is a separate TypeScript project from `src/`.** It's covered by `tsconfig.node.json` (not `tsconfig.app.json`) and by vitest's `include` (`scripts/**/*.test.ts`), which is how `scripts/optimize-images.ts` can import `node:child_process`, `node:fs`, and `node:path`. The trap: `tsconfig.app.json` sets `"types": ["vite/client"]` with no Node types, so **nothing under `src/` may import a `node:` module** — such an import passes `npm test` (vitest doesn't type-check) but fails `npm run typecheck` with TS2307 (cannot find module). This has cost real debugging time twice; if `npm test` is green but `npm run typecheck` fails on a `node:` import, the import is in the wrong tree.

## Conventions

- Components are function components with default exports, colocated in `src/components/`.
- Styling is Tailwind utility classes inline; the dark theme uses `gray-900`/`gray-950` backgrounds with `blue-*`/`purple-*` accents. **There is no `tailwind.config.js`** — v4 is configured from CSS, and this project adds no theme customisation at all, so `src/index.css` opens with a bare `@import 'tailwindcss'` and no `@theme` block. Content detection is automatic; there is no `content` glob to keep in sync. Custom utilities are declared there with `@utility` (not `@layer utilities`, which in v4 no longer generates variant-capable utilities); `postcss.config.js` loads `@tailwindcss/postcss` and no autoprefixer, since v4 handles prefixing itself.
- Type-only imports use `import type { ... }`.
